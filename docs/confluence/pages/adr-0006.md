# ADR-0006: Phase 4 ML — shadow-model scope and honest limitations

## Status
Accepted (Phase 4, in-process module — not a separate service).

## Context
The master brief specifies a shadow-model promotion pipeline: production model vs. shadow
candidate → comparison → false-positive evaluation → human approval → staged 5/25/50/100%
rollout. Phase 0/1 deferred a real ML scoring service (Python/FastAPI, a real model
registry, a real training dataset) as a separate container until Phase 4 (ADR-0002,
`docs/architecture/C4_DIAGRAMS.md`).

## Decision
Phase 4 implements the pipeline's **mechanics** for real — training, registration, shadow
scoring, comparison, drift detection, and a human-approval-gated rollout config — as an
in-process NestJS module (`apps/api/src/ml/`), not a separate Python/FastAPI service,
consistent with ADR-0003's modular-monolith stance ("avoid unnecessary microservices until
real load/team-topology justifies the split"). The model itself is a small,
dependency-free logistic regression classifier trained on
`docs/ml/ABUSE_SCENARIO_CATALOGUE.md`'s synthetic scenarios (`apps/api/src/risk/fixtures/abuse-scenarios.json`).

Feature parity between the rule engine (production) and the shadow model is achieved by
persisting the rule engine's actual `FactMap` (`risk_scores.facts`, added this phase)
rather than re-deriving an approximation — the shadow model is scored on the same features
the production rule engine actually used for that decision.

## What is real here
- Training: real gradient-descent logistic regression (`src/ml/training/logistic-regression.ts`),
  unit-tested against a hand-built separable dataset, not just "runs without throwing".
- Model registry: real Postgres-backed versioning (`ml_models` table), one row per trained
  version, holdout accuracy via leave-one-out cross-validation (the only honest method on a
  dataset this small).
- Shadow evaluation: real comparison against real, already-ingested `risk_scores` rows —
  not synthetic evaluation data.
- Drift detection: real comparison of production-vs-shadow score means over the evaluation
  rows just written.
- Human-approval gate: a rollout percentage can only be set via an explicit `ADMIN`-only
  API call, recording who approved it and when (`ml_rollout_config`).

## What is explicitly NOT real / not done, and why
1. **The trained model is not production-grade fraud ML.** The training set is ~6
   synthetic, hand-authored examples (Phase 3's scenarios 9-14) — enough to prove the
   pipeline's mechanics work end-to-end, nowhere near enough data for a model whose
   predictions should influence real enforcement. A real Phase 4 build-out needs a real
   (or realistically-simulated, consented) labelled dataset of thousands+ examples, a
   qualified ML engineer's feature-engineering review, and calibration/fairness testing
   across legitimate-use-case segments (Phase 0 §"Testing" already scopes this).
2. **The approved rollout percentage does not yet gate live traffic.** `risk.service.ts`'s
   ingestion path still always uses the rule engine only. Wiring `ml_rollout_config` into
   that path (routing `rolloutPercentage`% of real accounts' decisions through the ML
   model) is deliberately left undone — doing it silently, without a dedicated go-live
   review checkpoint, would mean an approved-for-shadow-testing model could start
   affecting real enforcement with no additional sign-off. This is a real, load-bearing
   gap, not an oversight: flagged rather than quietly wired in.
3. **No adversarial-resilience/anti-tampering work.** `docs/architecture/THREAT_MODEL.md`
   already flags SDK telemetry tampering as a Phase 4/Adversarial-Resilience item (brief
   §32) — model-extraction and adversarial-example attacks against the shadow model itself
   are equally out of scope here and need dedicated design work, not a checkbox.
4. **No real streaming feature pipeline.** Per ADR's Phase 3 note, features come from the
   batch feature store / the rule engine's `facts`, not a real-time feature-serving layer —
   fine for shadow evaluation on historical data, not sufficient for a low-latency
   production ML scoring path.

## Consequences
Phase 4's deliverable is a real, tested, working *pipeline skeleton* that a real ML/fraud
team can plug a real model into later, with the human-approval and staged-rollout scaffolding
already in place — not a claim that PriceGuard AI's fraud detection is now ML-powered in
production. Any future marketing or customer-facing claim to that effect requires the gaps
in this ADR to be closed first.
