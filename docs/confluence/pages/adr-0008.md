# ADR-0008: Phase 6 Enterprise Compliance — scope and what's genuinely tested

## Status
Accepted (Phase 6).

## Context
The master brief (§25) scopes SSO/SAML/OIDC/MFA, advanced RBAC, and DSAR tooling as Phase 6
"Enterprise Compliance" deliverables, explicitly deferred from the Phase 2 MVP (ADR-0002).
`docs/architecture/THREAT_MODEL.md` also already flagged "full session revocation list" as
a Phase 6 hardening item.

## Decision
Phase 6 implements, for real:

1. **OIDC SSO** (`src/sso/`) — a standards-compliant relying-party using `openid-client`:
   real discovery, PKCE (S256), nonce validation, and real id_token signature verification
   via the IdP's published JWKS. Tenant-configurable (issuer/client credentials never
   echoed back, even to the admin who set them).
2. **Fine-grained RBAC** (`src/rbac/`, `src/common/permissions.ts`) — named permissions
   layered on the fixed ADMIN/ANALYST/VIEWER roles, with per-tenant overrides (e.g. grant
   ANALYST the ability to decide appeals without making them ADMIN). Wired onto a real
   endpoint (`appeals:decide` on `POST /appeals/:id/decision`) as a working example, not
   left as an unused abstraction.
3. **DSAR self-service export** (`src/dsr/export.service.ts`) — the "right to
   access/portability" complement to Phase 2's erasure endpoint (ADR-0004): gathers every
   row of personal data this platform holds for one end-account into one export.
4. **Session revocation** — a `tokenVersion` claim on every JWT plus a
   `revoked_tokens` jti blocklist: single-session logout, "log out everywhere", and an
   admin-forced revocation of another user's sessions, closing the gap
   `THREAT_MODEL.md` flagged.

A real, previously-hidden gap was caught and fixed while wiring SSO: `tenant_users.role`
defaulted `ANALYST`; SSO-provisioned users now correctly default to the more conservative
`VIEWER` instead, since an IdP-authenticated identity has no tenant-side vetting of what
access level it should start with.

## What is genuinely tested (not asserted, verified)
- SSO: `test/sso.e2e-spec.ts` runs a **real fake OIDC provider**
  (`test/support/fake-oidc-provider.ts` — real HTTP server, real RSA keypair, real JWKS
  endpoint, real PKCE challenge verification) and drives the actual browser-redirect shape
  of the protocol: `GET /sso/:tenantId/login` → real 302 to the IdP → real 302 back with a
  code → `GET /sso/:tenantId/callback` → a real, working JWT. Also tests replay/forgery
  rejection (unknown state, single-use state).
- RBAC: `test/rbac-and-sessions.e2e-spec.ts` proves a real appeal decision succeeds under
  the default grant, then fails after an admin revokes it via a real override, over real
  HTTP against real Postgres.
- Session revocation: same file proves a logged-out single session gets 401 while a
  sibling session keeps working, and that an admin's forced revocation invalidates every
  session for the target user.
- DSAR export: `test/dsr-erasure.e2e-spec.ts` proves the export reflects real ingested
  data before erasure removes it, and that the export itself is audit-logged.

## What is explicitly NOT done, and why
1. **No real vendor IdP was exercised.** Okta, Azure AD, Auth0, and similar all have
   vendor-specific quirks (claim naming, discovery-document deviations, admin console
   setup) that only surface against the real service — this ADR's fake IdP proves the RP
   code implements the *protocol* correctly, not that it's been validated against a
   specific vendor. Before a real enterprise customer's rollout, budget time to test
   against their actual IdP.
2. **No SAML.** Only OIDC is implemented. SAML remains common in older enterprise
   environments; adding it is a separate, non-trivial relying-party implementation
   (different protocol entirely, not a config variant of OIDC).
3. **No MFA.** Brief §25 also scopes MFA; this phase does not add it. A real
   implementation needs a decision on TOTP vs. WebAuthn/passkeys vs. delegating to the
   IdP (SSO already delegates authentication decisions to the IdP, which may itself
   enforce MFA — that's a reasonable interim answer for SSO users, but local-password
   users have no MFA option at all right now).
4. **The SSO callback returns a JSON token, not a browser redirect into the dashboard
   SPA.** A production implementation would redirect back to the frontend with the token
   handled via a proper mechanism (e.g. a short-lived one-time code exchanged client-side,
   never a token in a URL fragment/query string that ends up in browser history/logs) —
   left undone rather than choosing an insecure shortcut under time pressure.
5. **Revoked-token/login-attempt rows are never purged.** Both `revoked_tokens` and
   `sso_login_attempts` grow forever; low-risk at real scale (short-lived rows, no
   attacker-controlled unbounded growth vector) but a real production deployment should
   add a cleanup job.

## Consequences
Enterprise-facing customers get a real, protocol-correct SSO integration point, working
fine-grained permissions, a real DSAR export, and closed session-revocation gap — with the
above limitations documented so a future phase (or a real customer's rollout) knows exactly
what remains before calling this "enterprise-ready" without qualification.
