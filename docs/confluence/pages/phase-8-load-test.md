# Phase 8 Load Test — real numbers, real environment, real caveats

Generated by running `apps/api/scripts/load-test-ingestion.ts` (`npm run load-test`) against
a real, fully-booted instance of this API — real Postgres (`priceguard_test`), real
bcrypt-backed API-key auth, real rule-engine scoring, nothing stubbed — using
[autocannon](https://github.com/mcollina/autocannon). See ADR-0010 for what this does and
does not prove.

## Environment this was run in (read the numbers against this, not in isolation)

This is the sandboxed development container used to build this project, **not** a
production-shaped host:

- 2 vCPUs, ~7.8 GiB RAM (`nproc` / `free -h`), shared with the API process, Postgres, and
  the load generator itself all on the same 2 cores.
- Single Postgres 18 instance, default `max_connections` (100), no PgBouncer/connection
  pooler, no read replica.
- API and load generator in the same process tree, same loopback interface — no real
  network latency, no load balancer, no TLS termination overhead.
- One API process (this project has never been run with more than one replica).

Real production numbers on real production hardware, with a network hop and TLS in the
path, will differ — likely quite a bit — from what's below. Treat these as **relative**
signals (did a fix help, where does the current implementation actually break down) rather
than an absolute capacity claim for any real deployment.

## Run 1: default configuration — a real concurrency bug found

First run: 20 connections, 15s duration, against the ingestion endpoint's out-of-the-box
rate limit (`@Throttle({ limit: 100, ttl: 60_000 })` in `risk.controller.ts`) with the
default `pg` pool.

**Result: massive real failures**, not rate-limit rejections — actual 500s:

```
100 2xx responses, 22445 non 2xx responses
```

Digging into the server logs (not just the 429s the throttle should have produced)
surfaced a **genuine, pre-existing concurrency bug**: `AccountsService.findOrCreateEndAccount`
and `AccountsService.findOrCreateDevice` both did a `SELECT` to check for an existing row,
then an `INSERT` if none was found — a classic check-then-act race. Under real concurrent
requests for the same `(tenantId, externalId)` or `(tenantId, deviceHash)` (exactly what
happens when a tenant's own client retries, double-submits, or simply sends two events for
the same account close together), two requests could both see "not found" and both attempt
the `INSERT`, and the second one failed its unique constraint
(`end_accounts_tenant_external_unique` / `devices_tenant_hash_unique`) with an unhandled
exception surfaced to the caller as a 500.

**This was a real bug in application code, not a load-test artifact** — it would have hit
any tenant sending concurrent requests in production. Fixed in this same commit: both
methods now do a single atomic `INSERT ... ON CONFLICT DO UPDATE`, which Postgres
guarantees is race-free regardless of concurrency (see the updated comments in
`apps/api/src/accounts/accounts.service.ts`). All existing e2e tests (36, across 11 suites)
still pass after the fix — no observable behavior changed for the non-concurrent case.

## Run 2: after the fix, rate limit raised for a raw-capacity read

`RISK_INGESTION_RATE_LIMIT=100000` (see the same-phase change making this limit
configurable via env), 20 connections, 15s duration:

```
2033 requests in 15.11s, 1.68 MB read, 0 errors, 0 non-2xx
Req/Sec:  avg 131.14, p50 140, p97.5 155
Latency:  avg 152.02ms, p50 142ms, p97.5 253ms, p99 473ms
```

Zero errors. The concurrency fix holds under sustained load. Raw throughput in this
2-vCPU sandbox environment is real but modest — each request does 5–7 sequential
round-trips to Postgres (find/create account, find/create device, insert session, insert
payment signal if present, read recent-session history, read active policy, insert risk
event, insert risk score, insert audit log entry) with `bcrypt.compare` on every request for
API-key auth, none of it currently batched or cached (see ADR-0010).

200 2xx responses, 118710 non 2xx responses

Exactly 200 = 2 × the configured 100-requests-per-60-seconds limit across a ~70s window —

## A second real gap found while writing the load-test harness itself

The load-test script originally closed the app (and its DB pool) immediately after
autocannon's `duration` elapsed. autocannon stops *sending new requests* at that point but
the server can still be draining a backlog of already-accepted connections — closing the
pool immediately produced real `"Cannot use a pool after calling end on the pool"` errors
for that in-flight backlog. This was a **load-test harness bug**, not an application bug —
a real client wouldn't trigger it — but it exposed a genuine, separate gap: **this API has
no SIGTERM-triggered graceful-shutdown drain** (`apps/api/src/main.ts` calls `app.listen()`
with no shutdown hook). In a real rolling deploy or autoscaling scale-down, in-flight
requests could be cut off mid-DB-transaction the same way. This is documented as an
explicitly-NOT-done item in ADR-0010, not fixed in this phase (see the ADR for why).

## Summary of real findings from this exercise

1. **Fixed**: a genuine check-then-act race in account/device upsert logic, found by real
   concurrent load, not by inspection — the kind of bug that's very easy to miss without
   actually generating concurrent traffic against a real database.
2. **Fixed**: the ingestion rate limit is now configurable per-deployment
   (`RISK_INGESTION_RATE_LIMIT` env var) instead of hardcoded.
3. **Fixed**: the Postgres connection pool size is now configurable
   (`DB_POOL_MAX`, `DB_POOL_IDLE_TIMEOUT_MS`) instead of relying on `pg`'s undocumented
   default of 10.
4. **Added**: `GET /healthz` (liveness, pre-existing since Phase 2) and
   `GET /healthz/ready` (new — real Postgres connectivity check) for a load
   balancer/orchestrator to use.
5. **Documented, not fixed** (see ADR-0010): no graceful-shutdown drain; the rate limiter's
   default in-memory storage is per-replica, not cluster-wide; no read replica / connection
   pooler; no horizontal-scaling test (this was never run as more than one process); no
   real multi-region deployment.
