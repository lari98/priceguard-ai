# ADR 0002: Phase 1/2 Technology Stack Selection

## Context
Master brief §24 requires researching current stable technologies before pinning versions, comparing alternatives, and explaining each choice, while §50 forbids blindly adding packages or using outdated dependencies without reason, and explicitly says to avoid unnecessary microservices and start modular. Versions below were verified directly against the npm registry and official release channels on 2026-08-18 (see command evidence in the repo's engineering log), not assumed from training data.

## Decision

| Concern | Choice | Version (verified 2026-08-18) | Rationale |
|---|---|---|---|
| Runtime | Node.js | 22.x (Active LTS) | Already the container runtime; current Active LTS line; native fetch/test runner reduce dependency count. |
| Language | TypeScript | **5.9.3**, not the published `latest` (7.0.2) | `npm view typescript dist-tags` shows `latest: 7.0.2`, a from-scratch native-compiler rewrite. `npm view ts-jest peerDependencies` returns `"typescript": ">=4.3 <7"` — the test-runner toolchain explicitly does not yet support TS 7. Shipping a decorator-heavy NestJS codebase on an unsupported compiler major is an unjustified risk for a production system; 5.9.3 is the newest version inside every tool's supported range. This decision must be revisited once `ts-jest`/`@nestjs/cli` publish TS 7 support. |
| Backend framework | NestJS | 11.2.1 (`@nestjs/core`, `@nestjs/common`, `@nestjs/testing`) | Opinionated module/DI structure maps directly onto the brief's module list (tenant, risk, policy, audit, appeals) without inventing our own conventions; first-class Guards/Interceptors give a natural home for tenant-isolation and audit-logging cross-cutting concerns; mature RBAC/Swagger/testing ecosystem. Alternative considered: Go (brief also lists this). Rejected for MVP because the team is starting from a discovery document, not existing Go infrastructure, and NestJS's decorator-based validation/DI reduces MVP boilerplate; Go remains an option for a future high-throughput scoring service if profiling shows Node is the bottleneck (kept as an open option, not a rewrite commitment). |
| ORM / migrations | ~~Prisma~~ → **Drizzle ORM + node-postgres** | **Superseded — see [ADR-0005](0005-drizzle-not-prisma.md).** Prisma 7.9.1 failed to generate its client in this build sandbox (`403` fetching its engine binary from `binaries.prisma.sh`, a hard external CDN dependency); replaced with `drizzle-orm` 0.45.2 + `drizzle-kit` 0.31.10 + `pg` 8.23.0, which have no native-binary/external-CDN dependency and were verified end-to-end (see ADR-0005 and the Phase 2 engineering log). | Type-safe schema-first migrations give an auditable, versioned schema history; kept as the requirement, just implemented without Prisma's binary-engine dependency. |
| Primary database | PostgreSQL | 18 (`postgres:18-alpine` container image) | Confirmed current major (18.4 patch release exists as of Aug 2026 per postgresql.org release notes) with strong JSON/JSONB support (needed for flexible rule/policy documents and evidence blobs), mature row-level-security features usable later to defense-in-depth multi-tenant isolation, and native partitioning for the high-volume `risk_events`/`audit_log` tables anticipated at scale. |
| Cache / rate-limit store | **Valkey** (Redis-protocol-compatible) | 8.x, wire-compatible with `ioredis` 6.0.0 client | Redis Inc. moved Redis itself to the non-OSI **SSPL/dual "Redis Source Available License"** starting 2024, which creates unresolved legal risk for a commercial B2B SaaS re-offering the software as part of a hosted service. Valkey is the Linux Foundation-governed, BSD-3-licensed fork maintained by the original Redis creators/AWS/Google, is wire-protocol compatible with the same `ioredis` client, and requires no code change versus "real" Redis. This avoids an unforced licensing question the master brief's own engineering-quality rules (§50, "do not blindly add packages") argue against introducing. |
| Streaming, analytics DB, graph DB (Kafka-compatible stream, ClickHouse, Neo4j) | **Deferred** | N/A | Per Phase 0 §M/N, these belong to Phase 3 (feature store/analytics) and Phase 5 (fraud graph), not the MVP. Introducing them now would violate the "avoid unnecessary microservices/complexity" instruction with nothing yet to justify the operational cost. |
| Frontend | Next.js (App Router) + React + TypeScript + Tailwind CSS | Next.js 16.3.1, React 19.2.8, Tailwind CSS 4.3.3 | Matches brief §24 exactly; App Router gives server components for dashboard pages that mostly read/aggregate data, reducing client bundle size for an internal admin tool. |
| API documentation | `@nestjs/swagger` (OpenAPI 3) | 11.4.7 | Generates the OpenAPI 3 spec required by brief §37 directly from the same DTOs used for runtime validation, keeping contract and implementation from drifting apart. |
| Validation | `class-validator` / `class-transformer` | 0.15.1 / 0.5.1 | Native NestJS pipe integration; declarative DTO validation keeps the ingestion API's input validation auditable and testable per-field (defends against injection/malformed-event classes of bugs, see SECURITY.md). |
| Auth (MVP) | `@nestjs/jwt` (dashboard sessions) + custom API-key guard (server-to-server) | `@nestjs/jwt` 11.0.2, `bcrypt` 6.0.0 for key/password hashing | SSO/SAML/OIDC/MFA (brief §25) are explicitly Phase 6 (Enterprise Compliance); MVP needs a real, correctly-hashed credential story, not a stub, so bcrypt-hashed API keys and JWT dashboard sessions are implemented now, structured so an OIDC provider can be added later without an auth-model rewrite. |
| Testing | Jest 30.4.2 + ts-jest 29.4.12 + Supertest 7.2.2 | — | Standard, well-supported NestJS testing stack; chosen specifically because it supports the pinned TypeScript 5.9.3 (see above). |
| Security middleware | `helmet` 8.3.0, `cors` 2.8.6, `@nestjs/throttler` 6.5.0 | — | Baseline OWASP-aligned headers, CORS allowlisting, and rate limiting from the first commit, per brief §25 and §50 ("do not sacrifice... for demo appearance"). |

## Alternatives considered
- **Go backend for MVP.** Rejected for now (see table); revisit if/when a dedicated high-throughput scoring service is justified by real load data (Phase 8).
- **Raw SQL migrations instead of an ORM.** Rejected: higher error risk for a small team and worse auditability of schema history than Prisma's migration log.
- **Real Redis (accepting SSPL terms).** Rejected due to unresolved commercial-licensing risk for a SaaS reseller use case; flagged in this ADR rather than silently avoided so it can be revisited with actual legal advice if a compelling technical reason to prefer Redis-proper ever appears.
- **Microservices split (separate risk-scoring service from day one).** Rejected for MVP: brief §24 explicitly says avoid unnecessary microservices; a modular monolith with clean module boundaries (mirroring the eventual service boundaries) is deliberately chosen so a future extraction is a refactor, not a rewrite.

## Security implications
API-key/JWT auth, helmet/CORS/rate-limiting are in place from the first backend commit, not retrofitted. Valkey over Redis-proper removes a licensing ambiguity that could otherwise surface during a future security/compliance/procurement review.

## Privacy implications
PostgreSQL's row-level-security and partitioning features are selected partly because they will be used to enforce/verify tenant isolation and retention-window deletion (§I of the Phase 0 document) at the database layer, not only in application code.
