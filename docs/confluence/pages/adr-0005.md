# ADR 0005: Supersede Prisma with Drizzle ORM + node-postgres

## Status
Supersedes the ORM row of ADR-0002 (technology stack), decided during Phase 2 implementation
(not Phase 1 planning), the day after ADR-0002 was written — recorded per `CONTRIBUTING.md`'s
"any non-trivial architectural decision gets an ADR" rule and the master brief's own
requirement not to silently change direction without a record.

## Context
While implementing the Phase 2 MVP, `prisma generate` failed in the build/CI sandbox with a
`403 Forbidden` fetching `schema-engine.gz` from `binaries.prisma.sh`. Prisma's client
generation depends on downloading a native Rust-based query/schema engine binary from
Prisma's own CDN at install/generate time — a **hard external runtime dependency beyond the
npm registry**, which is not guaranteed to be reachable from every locked-down CI runner,
air-gapped enterprise network, or (as observed directly) this project's own build sandbox.
`registry.npmjs.org` and `github.com` were both reachable from the same environment at the
same time, confirming this is specific to Prisma's engine-binary CDN, not a general network
outage.

## Decision
Replace Prisma with:
- **`drizzle-orm`** (0.45.2) as the query builder / schema definition layer — pure
  TypeScript, no native binary, no external CDN dependency at build or runtime.
- **`drizzle-kit`** (0.31.10) for migration generation — emits plain, human-reviewable
  `.sql` migration files under `apps/api/drizzle/migrations/`, rather than a proprietary
  binary-engine-driven migration format.
- **`pg`** (8.23.0, the standard node-postgres driver) as the underlying connection layer.

## Alternatives considered
- **Keep Prisma, work around the CDN block** (e.g., `PRISMA_ENGINES_CHECKSUM_IGNORE_MISSING=1`
  or a self-hosted engine mirror). Rejected: papering over a checksum-verification failure is
  itself a security downgrade (silently disabling integrity verification of a downloaded
  binary), and a self-hosted mirror is new infrastructure to build and maintain for no
  functional gain over an alternative that doesn't need one.
- **Raw `pg` with hand-written SQL and no query builder.** Rejected: loses type-safety
  between schema and query code, which is valuable for a schema this security/privacy-
  sensitive (see `docs/architecture/GDPR_DATA_MAP.md`) — Drizzle keeps that type-safety
  without the binary dependency.
- **Kysely.** A reasonable alternative with the same "no native binary" property; Drizzle was
  preferred for its more mature, actively maintained migration tooling (`drizzle-kit`) and
  larger ecosystem at time of writing.

## Advantages
No external binary CDN dependency at install/build/generate time — works identically in any
environment with npm registry access, including this build sandbox, locked-down enterprise
CI, and air-gapped internal networks with an npm mirror. Migrations are plain SQL files,
directly reviewable in a pull request by anyone who knows SQL, without needing familiarity
with a DSL-specific migration format — a small but real advantage for the compliance-review
audience this project explicitly designs for (DPOs, security reviewers, per Phase 0 personas).

## Disadvantages
Drizzle's ecosystem/tooling maturity (introspection, admin UI equivalents to Prisma Studio)
is somewhat less developed than Prisma's as of this writing; the team accepts this trade-off
in exchange for removing the external CDN dependency.

## Security implications
Removes a class of build-time supply-chain risk (a binary fetched from a third-party CDN,
outside the npm audit/Dependabot coverage that already protects the rest of the dependency
tree).

## Privacy implications
None beyond what ADR-0002/`docs/architecture/GDPR_DATA_MAP.md` already establish; the schema
itself (`apps/api/src/db/schema.ts`) is a direct, field-for-field port of the Prisma schema
this decision replaces, so the GDPR data map required no content changes, only a note that
the source-of-truth file moved.

## Follow-up finding: Prisma re-entered node_modules anyway (fixed)
Discovered while auditing the production `node_modules` tree for the Docker build
(`apps/api/Dockerfile`): `drizzle-orm` lists `@prisma/client` as an **optional peer
dependency** (its `drizzle-orm/prisma` adapter, which this project does not use — we use
`drizzle-orm/node-postgres` exclusively). npm's default behaviour auto-installs optional
peers when nothing else already satisfies them, so a plain `npm install` was silently
pulling in a full, unused Prisma 7.9.1 install (and, with it, three high-severity
`npm audit` findings against `prisma`/`@prisma/config`/`deepmerge-ts`) — exactly the
dependency this ADR says was removed.

Fixed with an explicit `"overrides": { "@prisma/client": false }` in
`apps/api/package.json`, which tells npm to drop that optional peer from the tree
entirely rather than auto-installing it. Verified: `npm ls prisma` after a clean
`rm -rf node_modules package-lock.json && npm install` shows no physical install (only the
override annotation), `du -sh node_modules` dropped from 424M to 349M, and
`npm audit --omit=dev` reports zero vulnerabilities (down from 3 high). Full unit + e2e
suites re-run clean after the change (see CHANGELOG.md).
